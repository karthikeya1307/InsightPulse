## Testing, Verification, and Improvements

Although AI was heavily involved in writing the code, running the application and testing its functionality were important parts of the development process.

Several issues were identified during execution and subsequently corrected. Some examples include:

| Testing Area | Issue Identified | Improvement Made |
|---|---|---|
| API testing | The health endpoint incorrectly counted database views as tables. | Updated the query to count only actual database tables. |
| Data ingestion | Some valid survey records were rejected because of future planned dates. | Adjusted the date validation logic to handle planned dates correctly. |
| Pipeline execution | The actions stage could not access predictions from an ongoing run. | Updated the current sentiment view to handle running and failed executions correctly. |
| Validation rules | Duplicate actions could be created for the same issue. | Added a database-level unique constraint with a documented exception. |
| Sentiment analysis | The phrase "not worth it" was incorrectly classified as positive. | Improved the handling of negated positive words. |
| Model evaluation | Macro-F1 scores were calculated incorrectly when certain labels were missing from a language slice. | Updated the evaluation logic to consider only labels present in that slice. |
| Dashboard testing | Some chart titles and legends overlapped, and text was not displayed properly. | Adjusted chart margins and title positioning. |
| API testing | Repeated reviews were accepted instead of being identified as duplicates. | Added duplicate detection and an appropriate HTTP 409 response. |
| Sentiment testing | Some clearly positive reviews were classified as negative. | Balanced the generated training data by adding more general positive and negative opinions. |
| Data validation | Issues from live API submissions were incorrectly reported as unexplained issues. | Separated live-submission issues in the validation report. |
| Full-scale testing | Some survey responses appeared after product discontinuation dates. | Updated the survey generation logic to respect product discontinuation dates. |
| Duplicate detection | Two generated reviews accidentally contained duplicate text. | Improved the generator to prevent accidental duplicates in the baseline dataset. |
| Performance testing | TF-IDF features were repeatedly fitted during model training. | Optimized the process to fit features once and reuse them. |
| Database performance | The actions stage took approximately 31 minutes due to inefficient database queries. | Reworked the database view and query execution strategy, reducing one query from over five minutes to approximately 0.6 seconds. |
| API evaluation | The evaluation endpoint could produce misleading results when the ground truth did not match the loaded dataset. | Added a validation check that returns HTTP 409 for mismatched datasets. |

These improvements helped identify issues that would not necessarily have been noticed by simply reviewing the generated code.

## Limitations and Areas for Improvement

There are a few limitations of the current implementation that are important to acknowledge.

- **Generated dataset:** The reviews and survey responses are generated using predefined templates. As a result, the training and testing datasets may share similar language patterns. This can make the evaluation results more optimistic than they would be with completely independent real-world data. The evaluation report in `docs/evaluation.md` discusses this limitation and includes an additional free-text evaluation.

- **Multilingual sentiment analysis:** Hindi and Telugu support currently uses a baseline approach based on character n-grams and a small sentiment lexicon. When the model has low confidence, human review is recommended. This provides basic language support but should not be considered equivalent to a fully developed multilingual sentiment analysis system.
